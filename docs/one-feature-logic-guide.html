One App Technical Logic Guide

Technical reference document for understanding the app implementation, feature rules, state flow, and route logic.

This document explains the current implementation in technical terms. It is intended to let you answer architecture, data-flow, feature-logic, storage, and validation questions about the app without reopening every source file first. The app is a static front end with a hash router, demo authentication, IndexedDB-backed local profile storage, and a Supabase-backed demo banking layer with browser-local fallback for balances, users, transactions, and remote demo profiles.

1. App Architecture

1.1 Routing model

The app uses a hash router. Navigation happens through URLs like #/home and #/payments. This avoids refresh problems on static hosting because the server only ever serves one HTML entry point.

  • router.js exposes currentPath() and go(path).
  • app.js maps routes to HTML files and loads the matching view into the main #app container.
  • After a view loads, initView(path) in views.js wires up the screen logic.

1.2 Route protection flow

The render flow applies several gates before a screen is allowed to load:

  • If the user is not signed in, they are sent to /login, unless they are on a public route.
  • If signed in but onboarding is incomplete, they are forced to /onboarding.
  • If onboarding is complete but the demo session is not unlocked, they are sent to /unlock.
  • If onboarding is complete but the tutorial is not finished, they are sent to /tutorial.

1.3 View initialisation

Every time a route loads, the app does the same common setup:

  • Remember the current and previous routes for custom back-button behaviour.
  • Hydrate theme and accessibility settings.
  • Mount the floating AI assistant.
  • Mount header shortcuts like the brand tap and avatar tap.
  • Show friend request notifications if new requests exist.
  • Dispatch to the route-specific initialiser such as initHome or initPayments.

2. Data Model and State Layers

2.1 Local profile state

The main user profile is stored locally through auth.js. This profile is the core state for personalisation and app features.

Important profile fields include:

  • Name, finance competency, helper choice, avatar, and onboarding flags.
  • Friend list and pending friend requests.
  • Shopping list items.
  • Budget pots with balances and goals.
  • Money Minutes quiz progress, XP, and streak.
  • Settings such as text size, high contrast, balance privacy, and theme.
  • Practice investing portfolio.
  • DM threads and unread counts.
  • A simulated local ledger used when money is moved in fake-only flows.

2.2 Remote demo banking state

remote.js is the remote banking adapter. It now reads and writes Supabase demo tables first, with localStorage fallback if the backend is unavailable. It stores or retrieves:

  • Demo users.
  • Current account balances.
  • Transaction history.
  • Simple profile records used to mimic remote persistence.

This matters because the app separates some banking-style actions from user preferences. For example, balances and transfers come from the remote banking layer, while onboarding choices live in the local profile.

2.3 Local vs remote money logic

The app mixes two money sources:

  • Remote account balance for the main current account and real demo transfers.
  • Local simulated ledger delta for fake internal adjustments such as pot transfers or some DM/demo flows.

The displayed available balance is effectively remote balance plus simulated delta. This lets the UI react to pot movements or fake flows without rewriting the seeded remote transaction history every time.

4. Storage, Persistence, and Data Contracts

4.1 IndexedDB layer

Local profile and auth state use assets/storage.js, which is a minimal IndexedDB wrapper. It opens database lloyds_one_db, version 1, with one object store called kv. It exposes asynchronous get, set, and del helpers. This means profile data survives refreshes and browser restarts.

4.2 Auth and profile keys

  • AUTH_KEY = auth_state
  • PROFILE_KEY = demo_profile
  • Both are stored via IndexedDB, not localStorage.
  • The demo user ID is fixed as demo_user_1.

4.3 Local storage keys used by the UI

  • chosenHelper: onboarding helper selection.
  • chosenInterests: comma-separated onboarding interests.
  • appMode: light or dark mode.
  • appTheme: background theme identifier.
  • friendReqSeenCount: count used for friend request notification logic.
  • insightsHomeCache: cached insights summary for the home card.
  • insightsActivePeriod: last selected insights period.
  • dmThreads: persisted DM thread object.
  • dmUnread: per-friend unread map.
  • incomingSeenAt: timestamp used to prevent repeating the same incoming-payment toast.
  • tutorialWalkthroughStep: live guided tutorial step index.
  • homeWidgetOrder: saved order of home widgets.

4.4 Session storage keys

  • demo_app_unlocked: current unlock-session flag.
  • routeCurrentPath: last rendered route.
  • routePreviousPath: previous route for back-button logic.
  • quizResult: summary payload for the quiz summary page.

4.5 Remote demo state contract

The browser fallback remote backend is stored under localStorage key demo_remote_state. That object contains:

  • users: array of demo users with IDs and names.
  • accounts: dictionary keyed by user ID to numeric balance.
  • transactions: array of transfer and merchant records.
  • profiles: simplified remote profile records with finance competency, interests, avatar, and helper.

4.6 Important local profile schema

The default profile created by defaultProfile() includes these core fields:

  • onboardingDone, tutorialDone, termsAccepted
  • name, financeCompetency, helper, avatarDataUrl
  • friends, friendRequests, friendDirectory
  • shoppingList
  • quizCompleted, learningXP, learningStreak
  • budgetPots as array of { id, name, emoji, balance, goal, color }
  • settings object for accessibility, privacy, theme, and notifications
  • locationCoords
  • simulatedLedger with balanceDelta and transactions
  • practicePortfolio with cash, holdings, selectedSymbol, and trades
  • dmThreads and dmUnread when persisted back from chat flows

4.7 How the database connects to the app

The project now uses two active persistence models plus one fallback layer:

  • IndexedDB path: auth and local profile state through assets/storage.js.
  • Supabase path: demo banking state through assets/supabase.js and assets/remote.js.
  • Fallback path: localStorage for remote demo banking state if Supabase is unavailable.

4.8 Active database connection path in the current app

The app now uses two live persistence layers:

  • IndexedDB through assets/storage.js for auth and local profile objects.
  • Supabase through assets/supabase.js and assets/remote.js for demo users, accounts, transactions, and remote demo profiles.

The connection sequence for local profile data is:

  • Feature code calls getProfile() or updateProfile() from assets/auth.js.
  • auth.js calls get or set from assets/storage.js.
  • storage.js opens IndexedDB database lloyds_one_db and object store kv.
  • The profile or auth object is read or written asynchronously.

The connection sequence for banking/demo data is:

  • Feature code calls helpers such as fetchBalance(), fetchTransactions(), or transferFunds() from assets/remote.js.
  • remote.js imports the Supabase client from assets/supabase.js.
  • On first use, ensureSupabaseSeeded() checks whether the demo tables are empty and inserts seeded demo users, accounts, transactions, and profiles if needed.
  • Reads and writes then go to Supabase tables demo_users, demo_accounts, demo_transactions, and demo_profiles.
  • If any Supabase operation fails, remote.js falls back to the browser-local demo_remote_state object in localStorage.

In practice, this means the runtime is now Supabase-first for banking/demo state, while still remaining resilient through local fallback.

4.9 Where Supabase fits technically

Supabase is now part of the active runtime path for the remote banking layer:

  • assets/supabase.js creates the browser client.
  • supabase/sql/demo_runtime_tables.sql defines the demo runtime tables the app now expects.
  • supabase/sql/profiles.sql still defines the separate real-style profiles table scaffold.
  • supabase/functions/account-admin/index.ts now targets the demo runtime tables for reset and delete actions.

The important technical distinction is that auth/profile state is still local-first through IndexedDB, while banking/demo state is Supabase-first through remote.js.

4.10 Supabase client wiring

assets/supabase.js imports createClient from the Supabase JavaScript SDK and constructs a client using SUPABASE_URL and SUPABASE_ANON_KEY. This client is now used by assets/remote.js for remote banking reads and writes.

4.11 Supabase profile schema

The provided SQL creates a public.profiles table with these columns:

  • user_id as primary key referencing public.users(id)
  • name
  • finance_competency
  • interests as text array
  • avatar_url
  • helper
  • updated_at

Row-level security policies allow users to select, insert, and update only their own profile row by matching auth.uid() to user_id.

4.12 Supabase edge function path

The edge function in supabase/functions/account-admin/index.ts expects a bearer token, verifies the user through Supabase Auth, then performs admin operations using the service role key. The implemented actions are:

  • reset: clears the demo runtime tables so they can be reseeded.
  • delete: clears the demo runtime tables for a full demo wipe.

The front-end helper callAccountAdmin() in assets/remote.js is aligned to the same demo-table model and still preserves local fallback behaviour.

4.13 Technical answer to “what database is the app using?”

The most accurate answer is:

  • User profile/auth state: IndexedDB in the browser.
  • Banking/demo backend: Supabase demo tables.
  • Fallback banking layer: localStorage in the browser.

5. Boot Sequence and Navigation Control

5.1 Render sequence in app.js

The app render process is deterministic and follows this order:

  • Read the current hash route.
  • Mount the bottom navigation if it has not been mounted already.
  • Toggle nav visibility depending on whether the route is nav-managed.
  • Map the current route to the correct active nav tab.
  • Fetch auth state.
  • Apply route guards for sign-in, onboarding, unlock, and tutorial.
  • Fetch the HTML partial for the route.
  • Insert that HTML into #app.
  • Run initView(path) to attach behaviour.

5.2 Back navigation implementation

Back behaviour is route-aware rather than browser-history-only. rememberRoute(path) stores current and previous routes in session storage. backTargetFor(path) first checks whether the route is in the no-back set, then checks the remembered previous route, then falls back to a hard-coded route map. This is why nested screens such as pot detail, transaction, and quiz screens always navigate somewhere sensible even if they were opened directly.

5.3 Bottom navigation details

The bottom nav is generated in JavaScript, not hard-coded in each view. It contains five top-level destinations: Home, Payments, Money Minutes, Deal Nest, and DMs. The active highlight is a movable indicator. Dragging the indicator across the nav computes the nearest button based on pointer X position and routes there on release.

6. Global UI Systems

Bottom navigation

The bottom nav is mounted once and reused across screens. It highlights the active top-level route and includes a draggable active indicator. Some screens map back to a parent tab. For example, /insights maps to the Payments tab, and quiz routes map to the Money Minutes tab.

Back navigation

The app does not rely only on browser back. It stores the current and previous routes in session storage and uses fallback targets for screens like pots, transactions, and settings so the custom top-left back button always has a sensible result.

Settings and theming

Accessibility and appearance settings are stored in the local profile. They are applied globally by setting HTML attributes and CSS variables. This includes text size, contrast, reduced motion, larger tap targets, background theme, custom background, and hidden balances.

Assistant widget

The AI chatbot is a simulated assistant mounted on every view. It builds a live snapshot from the current profile, pots, recent transactions, unread DMs, and practice portfolio state. It then uses rule-based intent detection to return a structured response card with a title, body, bullets, and route actions. It is not calling a real language model in this demo.

7. Entry Flow Features

Splash

The splash screen waits briefly, checks auth and onboarding state, and then routes the user to login, onboarding, unlock, tutorial, or home. It acts as the first decision point for the entire app.

Login

Sign-up and sign-in are demo implementations. After either action, the app ensures the local profile exists, ensures the remote demo user exists, and then synchronises name, finance competency, interests, and avatar between the two layers.

Onboarding

The onboarding flow is two-step and writes both personalisation and control flags.

  • Step 1 chooses the helper mascot.
  • Step 2 captures name, finance confidence, interests, optional location, and terms acceptance.
  • The name field actively blocks numeric input at keystroke, paste, and sanitisation level.
  • At least two interests are required.
  • Terms must be accepted before finishing.
  • Informational links open modal popups explaining competence-based logic, interest-based logic, location use, and feature terms.

When finished, onboarding stores interests locally, updates the local profile, updates the remote name, pushes a remote profile record, sets the location setting if coordinates were granted, unlocks the demo session, and routes to the tutorial.

Unlock

This is a demo lock screen. The hard-coded passcode is 1234. A Face ID button simulates biometric success with a timed overlay animation. Successful unlock sets a session flag rather than changing the long-term profile.

Tutorial and guided walkthrough

The tutorial page starts a guided walkthrough across live screens. Each walkthrough step stores its index in localStorage, routes to the relevant page, highlights one selector, and shows an overlay card explaining that feature. Finishing marks tutorialDone true and sends the user into the live app.

8. Home Screen Logic

8.1 Home entry points and action wiring

initHome() binds all major dashboard actions at initialisation time. These include send money, add money, open pots, open shopping list, open practice investing, open Money Minutes, and open Insights. It also dynamically injects a top-level settings button and a Wrapped button if they are not already present in the top action area.

The home screen is the main dashboard and combines several independent systems.

8.2 Balance card

  • The main account card flips to reveal details on the back.
  • Its height is synchronised to the tallest face so the flip content is not cut off.
  • The displayed name on the card is derived from the first word of the full profile name.
  • The current implementation caps the dynamic card height to keep the card compact on the home screen.

8.3 Remote snapshot loading

Home tries to combine remote banking data and the local simulated ledger into one coherent view. If a remote user exists, it loads the remote balance and remote transactions, merges in simulated transactions, sorts them by date, and updates the visible balance. If remote sync is unavailable, it falls back to a local-only interpretation.

The internal support functions that make this work are:

  • getSimulatedLedger(): reads the local balance delta and simulated transactions.
  • syncPendingBalanceDelta(): attempts to push pending local balance delta into the remote balance when possible.
  • getAvailableMainAccountBalance(): returns the effective current-account balance after applying the ledger delta.
  • findTransactionById(): resolves a transaction from either remote or local simulated sources.

8.4 Transactions section

  • Transactions are tagged as income or expense depending on direction.
  • The filter buttons switch between all, income, and expense.
  • The screen shows a limited preview by default and expands when the user taps view all.
  • Incoming remote transfers can trigger a top notification that opens the receipt view.

8.5 Pot summary

Home renders up to three pot preview cards plus a New Pot tile. Progress is calculated as current pot balance divided by goal, capped at 100%.

8.6 Home widget arrangement

The dashboard widgets can be reordered through a drag-and-drop arrange mode. The resulting order is stored in localStorage and reused on future visits.

9. Account and Profile Features

The account page is the personal profile control centre.

  • Displays name, email, finance confidence label, interests, and account creation date.
  • Supports avatar upload through a local data URL.
  • Avatar updates are also written to the remote profile record.
  • Includes shortcuts to friends, the tutorial, and the dataset page.
  • Supports sign out, reset, and delete actions.

10. Dataset and Admin Features

Lloyds dataset page

This page loads a demo dataset overview plus product, customer, transaction, and hotspot lists. It behaves like a read-only reporting view. The data is currently returned from helper functions in remote.js.

Admin console

The admin console gives you direct control over demo state. It can set the demo balance, create demo transactions, trigger quick canned events like wages or groceries, and reset the demo dataset. It also clears cached insight summaries so analytics reflect the new data.

11. Payments and Money Movement

Send Money

Payments loads the friend list as valid recipients and prevents several bad cases before sending:

  • No recipient selected.
  • Trying to send money to yourself.
  • Invalid or zero amount.
  • Amount greater than available main account balance.

If the recipient is a real demo user, the app uses the remote transfer function. If the recipient is marked fake, the app records a local simulated transfer instead. In both cases the user gets a confirmation and a receipt shortcut.

The execution sequence is:

  • Load recipient options from the user’s friend list.
  • Resolve a preselected friend from the route query string if present.
  • Parse and sanitise the amount from the text input.
  • Resolve whether the target is a real or fake friend.
  • Run all guard checks.
  • Execute transferFunds for real recipients or recordSimulatedTransfer for fake ones.
  • Show confirmation toast and receipt deep link.

QR payments

QR sending and receiving is presentation-only. One modal shows a fake personal QR code. Another opens a live camera preview if the device allows it, but no QR content is actually parsed.

Transaction details and receipt

The transaction page loads a transaction by ID, infers whether it is incoming or outgoing, and renders a standard transfer detail view. The receipt button opens a modal with amount, counterparty, date, status, and reference.

Add Money

This is a navigation hub rather than a deposit engine. It links into cheque scanning, moving money from a pot, and adding money into a pot.

Scan Cheque

The cheque page attempts to open the device camera and falls back to a poster image if that fails. Capturing simply shows a success confirmation in the current demo.

12. Budgeting Pots

Budget Pots overview

Pots live inside the local profile. The overview page calculates a total pot balance, renders all pot cards, and opens detailed pot pages.

Create Pot

Creating a pot requires a name and builds a new object with an ID, emoji, colour, optional goal, and zero starting balance. New pots are appended to the profile and the user is routed into that pot immediately.

Pot Detail

The detail page reads the pot by ID, paints the hero area with the saved pot colour, and calculates the progress percentage from current balance versus goal.

Move money from a pot

This flow takes money out of the selected pot, checks the amount is valid, checks the pot has enough balance, then deducts the amount from that pot and applies a positive simulated balance adjustment to the main account.

Add money into a pot

This flow moves money from the main account into a pot. It checks:

  • A pot is selected.
  • The amount is valid.
  • The main account has enough available balance.
  • If the pot has a goal, adding the amount will not push the pot above that goal.

If the pot reaches its goal after the transfer, the app shows a completion notification.

Technically, pot-to-main and main-to-pot movements are not remote bank transfers. They are local pot mutations plus an opposite-signed simulated balance delta so the main balance stays visually correct.

13. Friends, Profiles, and DMs

Friends page

The friends page has three jobs:

  • Render pending friend requests with accept or decline actions.
  • Render the current friend list with send money, split bill, and message shortcuts.
  • Search the remote user directory and allow new requests to be added.

Friend profile

The friend profile page reads the selected friend and fabricates a presentable payment identity from their ID and name, including sort code, masked account number, and a payment reference label. It is mainly a trust and confirmation screen before sending money.

DMs

DM threads are stored locally and persisted back into the profile. Messages support three types: text, payment, and request.

  • Unread counts are tracked per friend.
  • Opening a thread clears that friend’s unread count.
  • Sending a request creates a request-type message only.
  • Sending money checks main account affordability before creating the payment message.
  • Incoming messages can trigger top notifications.
  • A Taylor Brooks demo branch auto-replies and simulates an incoming payment after a text message.

The internal DM thread object is effectively:

  • Dictionary key = friend ID
  • Value = ordered message array
  • Each message holds ID, timestamp, type, direction, text, and optional amount

14. Bill Splitting

Bill splitting is a guided local flow built on top of a fixed list of sample transactions and the user’s friend list.

  • The user selects a transaction and one or more friends.
  • The app shows the payer as Me and calculates the per-person share as total divided by total attendees.
  • The split page explicitly shows who paid and who owes.
  • When the split is sent, the app writes request messages into the selected friends’ DM threads.

15. Shopping List and Grocery Comparison

The shopping page combines a personal list with nearby grocery deal data loaded from a JSON file.

  • The user can type custom items or add deal results directly.
  • Duplicate list entries are prevented by case-insensitive normalisation.
  • The search results can be filtered by grocery name, brand, store, or category.
  • The comparison logic groups results with the same normalised item name and sorts each group by price.
  • The UI highlights the best nearby option and shows when another listing is more expensive than the cheapest equivalent.
  • The page also changes section order depending on whether the user is actively searching.

Comparison works by building a map keyed by normalised item name, sorting each group by ascending price, and then using the first entry as the cheapest option. Result cards compare each visible item against that cheapest entry.

16. Deal Nest

Deal Nest loads student deals from a JSON file and then personalises what is shown based on onboarding interests.

  • Interest tags are mapped to broader categories like Food, Travel, Tech, and Entertainment.
  • The hero text and featured deals adapt to those interests.
  • The filter chips switch between Featured and category views.
  • Search matches title, brand, category, summary, and interest tags.
  • Results are sorted by popularity.
  • Each deal has a copy-code action, and the UI labels every code explicitly as Code:.

17. Money Minutes and Quizzes

Money Minutes feed

Money Minutes is implemented as a vertical reels-style learning feed. The static page handles sound toggles for embedded videos. The main live route is the /learn page, which builds a larger dynamic feed.

Learning track personalisation

Learning modules are filtered by finance competency:

  • Beginner users see simpler modules first.
  • Comfortable users get a broader set including some intermediate material.
  • Confident or expert users are biased toward harder modules.

Dynamic reel generation

The learn page generates lesson reels and periodically inserts quiz reels into the scroll. Some reels use real video files, and others use designed placeholder panels with educational copy. Explain buttons open the assistant with a preset explanation.

The learn feed is assembled from two sources: competency-filtered lesson modules and quiz queue items derived from the module quiz IDs. Every three lesson reels, one quiz reel is inserted if quiz data exists.

Quizzes and challenge mode

Quizzes are defined in a shared question bank. The app supports:

  • Module-specific quiz lists.
  • Video intro pages before each quiz.
  • Question-by-question quiz screens.
  • A summary screen that awards XP and streak progress.
  • A cross-module Quiz all challenge that flattens all questions into one sequence.

18. Practice Investing

Practice Investing is a self-contained simulator that uses fake assets, fake prices, fake holdings, and fake cash.

  • The starting wallet is £10,000 equivalent in demo cash.
  • Assets include stocks, an ETF, and crypto.
  • Price histories are generated synthetically from each asset’s base price and drift value.
  • A timer updates the latest price every 1.8 seconds to simulate a moving market.
  • The order ticket calculates order value and projected cash after the trade.
  • Buying checks that the fake wallet has enough cash.
  • Selling checks that the user owns enough units.
  • Average entry price, open positions, and unrealised PnL are recalculated after trades.
  • The portfolio persists into the local profile.
  • A guided overlay explains the main parts of the investing UI.

Holdings are stored per symbol with quantity and averagePrice. PnL is always unrealised and is computed as current market price minus average entry price times position quantity.

19. AI Insights

AI Insights builds an analytics dataset by combining real demo transactions and synthetic finance records from a JSON file.

  • Transactions are classified into categories by keyword matching.
  • The page supports week, month, and year windows.
  • For each period it calculates total spend, income, safe-to-spend, category totals, and trend bars.
  • It draws a donut chart, mini spark bars, and interactive bar chart readouts.
  • The analysis text is generated from templates using simple logic such as momentum, top-category pressure, and net movement.
  • The resulting summary is cached for the home-screen mini insights card.

The insights page is not a real ML pipeline. It is deterministic analytics plus template-driven commentary. The reason it feels intelligent is that it combines real transaction direction, keyword category classification, synthetic fallback data, and several computed aggregates into coherent analysis sentences.

20. Spending Wrapped

Spending Wrapped creates a month-style recap from the last 30 days of expense transactions. It classifies categories, totals top merchants, finds the heaviest spending day, calculates the top three categories, and assigns a spending persona from a themed lookup table. If there is not enough real data, it falls back to an example summary based on the user’s interests.

21. Settings and Session Controls

Settings persist user-level preferences and account controls. Main logic includes:

  • Light or dark mode selection.
  • Preset or custom background theme selection.
  • Accessibility toggles like text size, contrast, motion, and larger targets.
  • Privacy and notification toggles such as hidden balances and payment alerts.
  • Reset account, simulate onboarding, sign out, and delete account flows.
  • Optional navigation into the admin console.

22. Notification, Modal, and UX Infrastructure

Several cross-cutting utility functions make the app feel coherent:

  • showActionModal(): standard single-action alert-style modal for blocking messages.
  • showContentModal(): richer modal for receipts, onboarding terms, QR code views, and other content-heavy panels.
  • showTopNotification(): transient toast/notification layer, with optional action callback.
  • showConfirmation() and showToast(): lightweight positive feedback layers.

These utilities are used throughout the app instead of route-specific ad hoc messaging, which keeps confirmation and error handling consistent.

23. Important Business Rules Across the App

  • You cannot send money to yourself.
  • You cannot send more than the available current account balance.
  • You cannot move more money out of a pot than that pot contains.
  • You cannot add more money to a pot than its goal cap if a goal exists.
  • Onboarding requires at least two interests and accepted terms.
  • Name entry during onboarding does not allow numeric characters.
  • Practice investing never uses real money.
  • AI features are guided demo logic, not regulated financial advice.

24. What Is Demo Logic vs What Feels Real

The app intentionally mixes realistic UX with simplified implementation.

  • Feels real: navigation, balances, transactions, flows, receipts, profiles, settings, and persistence.
  • Demo logic: hard-coded passcode, simulated chatbot, generated prices, fake cheque capture, fake QR scanning, sample bill transactions, and seeded dataset records.
  • Hybrid logic: remote-style transfers and balances are persisted, but still inside a local demo backend.

25. Technical Q&A Cheat Sheet

25.1 Where does most feature logic live?

In assets/views.js. The file is effectively the application controller layer.

25.2 What persistence technologies are used?

IndexedDB for auth/profile state, Supabase for demo banking state, localStorage for UI caches and remote fallback state, and sessionStorage for current session state such as unlock status and route memory.

25.3 Is there a real backend?

Yes for the banking/demo layer. The runtime now uses Supabase demo tables through assets/remote.js, while auth and local profile state still live in IndexedDB.

25.4 How are balances kept in sync when pots move money?

Pot balances mutate locally in the profile. The current account display changes through simulatedLedger.balanceDelta, which is added to the remote current account balance when the app renders balances.

25.5 How are fake transactions different from remote transactions?

Fake transactions are stored inside the local simulated ledger and use local_user as one side of the transfer. Remote transactions are stored in Supabase demo tables and use seeded demo user IDs, with browser-local fallback if needed.

25.6 How does onboarding personalisation affect later screens?

29. Application Architecture and Overall System Planning

29.1 High-level architecture

The app is structured as a browser-based single-page application with a thin routing shell, a large controller layer, a local user-state layer, and a remote demo-banking layer.

  • Presentation layer: HTML partials in views/ plus shared styling in assets/styles.css.
  • Routing layer: assets/router.js and assets/app.js.
  • Controller layer: assets/views.js, which binds DOM events, transforms state, validates actions, and drives navigation.
  • Local persistence layer: assets/auth.js plus assets/storage.js over IndexedDB.
  • Remote persistence layer: assets/remote.js plus assets/supabase.js over Supabase demo tables.
  • Static content layer: JSON data files for deals and insight simulation inputs.

29.2 Runtime request and event flow

A normal user interaction flows through the system in this order:

  • The router changes the current hash route.
  • app.js loads the relevant HTML partial.
  • initView(path) selects the correct route initialiser.
  • The route initialiser reads local profile state and, when required, remote banking state.
  • User interactions trigger validation logic inside views.js.
  • Successful actions write back to IndexedDB, Supabase demo tables, or both.
  • The UI then re-renders the affected section or navigates to the next route.

29.3 Separation of concerns

The intended logical split is:

  • auth.js owns user-facing profile state and demo session lifecycle.
  • remote.js owns bank-style records such as balances, users, transactions, and remote profile mirrors.
  • views.js owns user journeys, validation, orchestration, and presentation-side business rules.
  • app.js owns route loading and access control at the app-shell level.

In practical terms, views.js currently does more than a strict controller layer would in a larger production system, but the separation is still clear enough to explain system behaviour.

29.4 State domains

The app has three important state domains:

  • Session state: unlock status, route memory, and temporary quiz results in sessionStorage.
  • User state: onboarding, settings, friends, pots, DM threads, and learning progress in IndexedDB profile storage.
  • Banking state: balances, transactions, remote demo users, and mirrored demo profiles in Supabase demo tables, with local fallback.

29.5 System planning assumptions

The implementation suggests the app was planned as a financial super-app demo with multiple feature verticals sharing one account identity and one navigation shell.

  • Core money vertical: balances, transfers, transaction history, receipts.
  • Budgeting vertical: pots, moving money, add-money flows.
  • Social money vertical: friends, DMs, split bills, peer-to-peer actions.
  • Discovery vertical: Deal Nest and shopping comparisons.
  • Education vertical: Money Minutes, quizzes, practice investing, AI insights, wrapped analytics.
  • Control vertical: onboarding, settings, account page, admin console, tutorial.

29.6 Why the architecture is shaped this way

The architecture is optimised for rapid prototyping and demo coherence rather than strict enterprise modularity.

  • HTML partials make it easy to iterate on screens quickly.
  • A single route initialiser file reduces coordination cost during fast UI changes.
  • IndexedDB avoids needing full backend identity setup for profile state.
  • Supabase demo tables give the banking layer a real external persistence target.
  • Local fallback keeps the demo usable even when backend connectivity is incomplete.

29.7 Current architectural strengths

  • Fast to iterate on product flows.
  • Clear route-to-screen mapping.
  • Reasonable separation between local user state and remote banking state.
  • Easy to explain because the main flow is explicit rather than hidden in framework abstractions.
  • Resilient demo behaviour because remote persistence has local fallback.

29.8 Current architectural weaknesses

  • views.js is large and highly centralised.
  • Feature logic, presentation wiring, and orchestration live very close together.
  • Some domain rules are encoded directly inside route handlers instead of reusable domain services.
  • The system mixes true persistent data, demo data, and simulated data, which is useful for a demo but increases conceptual complexity.
  • Supabase auth and the demo identity model are not fully unified.

29.9 System boundary summary

If you need to explain the system boundary concisely, the clean version is:

  • The browser renders all UI and owns orchestration logic.
  • IndexedDB stores user-local profile and preference state.
  • Supabase stores shared demo banking state.
  • localStorage acts as a resilience and simulation layer when the remote path is not available.

29.10 Best concise architecture explanation

A strong short technical explanation is:

“The app is a vanilla JavaScript single-page app with route-based HTML partial loading. It uses IndexedDB for local user/profile state, Supabase-first demo tables for banking state, and a large controller layer in assets/views.js to connect routes, validation, persistence, and UI behaviour.”
